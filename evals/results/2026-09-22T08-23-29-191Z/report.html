The trap to avoid: you may see **1,536** quoted somewhere. That's a different mechanism — it's the *listing* truncation for `description` + `when_to_use` combined (configurable via `skillListingMaxDescChars`). A 1,200-char description will look fine in the listing and still hard-fail on upload. Author against 1,024.

Practical targets:

- **Minimum 80 chars** (enforced by the audit script) — shorter than that isn't a trigger surface, it's a label.
- **≤ 500 chars** for anything that isn't a primary routing skill. Only top-level routing skills earn more.
- Put the most important trigger first. Every listed description is paid on *every turn* out of the shared always-loaded budget, so length is a recurring tax, not a one-time cost.

Content rule: a description carries **triggers and anti-triggers only**. Entity lists, option catalogues, technique enumerations belong in the body or `references/`. If your description needs `when_to_use` to fit, it usually needs cutting instead — `when_to_use` buys readability, never budget, since it counts against the same combined listing cap.

One thing worth knowing if this skill ships in a plugin: consumers have no lever to trim a plugin skill's description. `disable-model-invocation`, `skillOverrides: name-only`, and `paths:` all work on project skills and none of them reach a plugin skill (measured today). Your listing cost is a tax downstream users can't negotiate short of disabling the whole plugin — so write it tight.

The `description` field in a SKILL.md frontmatter can be up to **1024 characters**. (The `name` field is capped at 64 characters, lowercase letters, numbers, and hyphens.)

A few practical notes:

- **The whole description is always in context.** Every installed skill's name + description is loaded into the system prompt at startup — that's how the model decides when to invoke it. So the cost of a long description is paid on every turn, whether or not the skill fires.
- **Use the budget when triggering is ambiguous.** Descriptions that pack in concrete trigger terms genuinely help. The `dataviz` skill in this session is close to the limit and spends nearly all of it listing trigger phrases ("chart", "heatmap", "sequential / diverging palette", …) — worth it because the model otherwise wouldn't know to load it before writing chart code.
- **Keep it short when the name already says it.** `init` gets by with one line.
